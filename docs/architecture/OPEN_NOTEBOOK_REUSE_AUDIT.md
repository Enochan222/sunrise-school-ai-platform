## Critical build-vs-reuse boundaries

**Direct reuse in A (under private deployment):** SurrealDB migration engine and notebook/source models, content-core extraction, notebook indexing, text/vector search, upload/status/retry/download logic, notes, basic transformations, provider/credential & model management, worker and existing UI components. Start with user-supplied source ZIP and pinned official release; NEVER install unbounded `latest` without reproducible digest.

**Thin A-specific policy layer still essential:** `(school_id, content_shell_id, notebook_id)` mapping; server-side authorization before *every* search/download/preview/SSE; source ownership post-filter; one logical owner/source, no cross-Shell source graph; immutable source versions/rights/publish state; explicit A original backups and A API with strong service identity. Unscoped global search/list must not be reachable through Sunrise. Existing source `updated_at` is not an immutable `SourceVersion` provenance object.

**Build in B, not A:** academic Course/Class/TeachingGroup, enrollment, Assessment/Draft/Grade Ledger, subject question/rubric contracts, B AI credential store and generation queue, four-subject exam generation, submission/marking, analytics, teacher IAM, approved real PII. Open Notebook Transformations are optional teaching-material utilities, not authoritative grades or papers.

**I/U only:** I orchestrates existing A/B versioned APIs, binding saga, scoped evidence and teacher read-only access. U presents them but cannot bypass staff/business permissions or call ON API directly. Reusing Open Notebook React UI components is a build accelerator only if API Client and security boundaries are replaced and regression tested.

## 6 specific no-go traps (adversarial)

1. **Unsafe default config:** `api/auth.py` skips password protection when secret missing; Docker exposes UI/API ports, SurrealDB root:root fallback and encryption-key placeholder. S1 deploy must override and isolate; do not use native password as course IAM.
2. **Global search/list:** `api/models.py:39` and `resolve_notebook_scope` treat no scope as whole vault. `GET /sources` without notebook ID is a global listing; `GET /notebooks` lists all. S1 must deny unsafe raw paths and prove source ownership.
3. **Source can be associated with multiple notebooks:** `SourceCreate.notebooks` and native add-source links permit it; S1 A must ensure one logical Source owner even if upstream supports multi-notebook references.
4. **Original file deletion:** native Source deletion can remove uploaded asset; `SourceCreate.delete_source` flags can remove source file on processing. Sunrise's Archive / retention and restore are distinct from upstream hard delete.
5. **Queue completeness:** A's `CommandService.list_command_jobs()` returns `[]`, `cancel_command_job()` returns True without actual cancellation in provided source. It does not fulfill B job audit/cancellation SLAs; do not reuse B queue.
6. **Citations not immutable evidence:** upstream `SearchResponse.results: List[Dict[str,Any]]`; no formal `source_version_id, content_sha256, citation_locator` guarantee. S2 versioning + S9 evidence is real new work; ON Ask output is not sufficient evidence of correct school exam questions.

## AI/provider choices — avoid duplicated work

A's **own** optional embedding/chat use can reuse Open Notebook's provider credentials/configuration UI and model APIs behind private Admin access. It need not invent an extra A provider store. B's S7 provider credentials are **separate** because B owns authoritative paper/marking jobs and must not use A's DB or root key. Even if the same person uses the same Gemini account, secret rotation, metering, consent and audience must remain separate. A shared secret manager is a **future explicit design choice**, not implicit A↔B password reuse. Text-only A search must be actually demonstrated without assuming an AI model is available. Optional OCR/Docling and cloud models require real file test and school policy approval.

## Optional existing capabilities not part of core 29 Stages

Open Notebook already offers source chat, text transformations, notes, insight generation and podcasts. They can later be exposed as **A-owned approved optional features** after rights/usage/cost review; do NOT insert them into S1/S2 acceptance or silently expand B question creation scope. Future Audio/PTH multimedia features can start by assessing its podcast/TTS capabilities before creating new media tooling. External `Math-paper` and `PTH_Homework` are **references**, not production-ready integrated modules or proof of permission correctness.

## Confidence and verification method

**Confirmed:** route/model/worker behavior visible in supplied source ZIP; latest upstream release notes indicate similar capabilities. **Inference:** reuse-first reduces duplicate implementation scope but does not prove integration complexity or model quality. **Not run:** actual Docker, PDF/OCR, multi-model compatibility, Source Browser/API bypass, SurrealDB Restore, B Postgres, service JWT/ACL, E2E. To freeze S1, compare to pinned upstream commit/image digest, run exact tests, and keep a provider/fork compatibility matrix for upgrades.

**Explicit SourceVersion boundary:** Native source timestamps and topics are not immutable school-approved version IDs; Sunrise A must preserve its own SourceVersion identity, rights, and content hashes.

## Adjacent code reuse in B (not sharing A data)

Open Notebook's LLM Provider layer uses the standalone `Esperanto` multi-provider library. B may **evaluate using the library directly** for standardised Gemini/LLM calls and structured responses rather than writing N provider-specific HTTP clients. This reuses a library, NOT A SurrealDB credentials or A-specific service account. Pin library version, verify license and actual Gemini structured-output validation before S7/S8 acceptance. Official upstream context: `https://github.com/lfnovo/esperanto`.

For B's independent PostgreSQL/Supabase service, **Supabase Auth, Postgres constraints/RLS, Supabase Storage, Supabase Queues (`pgmq`)** are candidate managed building blocks. Do not write a custom authentication/queue/file-bucket engine before evaluating them. However RLS and Auth do not automatically supply Sunrise school/course/group grants; pgmq's visibility-window delivery does not ensure exactly-once business artifact effects; Grade Event concurrency and approval remain B-owned domain logic. Official reference: `https://supabase.com/docs/guides/queues`, `https://supabase.com/docs/guides/auth`.
